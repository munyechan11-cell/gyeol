# 결(Gyeol) 아키텍처 — 현재 상태와 이행 계획

이 문서는 "코드를 신 버전으로 갈아엎는다"는 결정을 실행 가능한 순서로 옮긴 것이다.
방식은 **점진 이행**이다. 파일럿 매장이 실제로 영업 중이므로, 어느 단계에서 멈추더라도
서비스가 돌아가는 상태를 유지한다.

5. **타입 안전망이 꺼져 있었음** — `strict` 미설정. Phase 0 에서 해소했다.

## 목표 아키텍처

**Next.js App Router + Supabase(Postgres).**

> 2026-09 방향 변경. 원래는 "Next.js 로 가되 Firebase 는 유지"였다. 근거는
> "이 앱은 onSnapshot 실시간이 본질이라 Firestore 를 대체하려면 실시간 계층을 새로
> 만들어야 한다"였는데, 그건 Postgres 에 실시간이 없다는 전제였다. Supabase Realtime 이
> 그 자리를 채우므로 전제가 성립하지 않는다. 게다가 남아 있던 두 문제가 Firebase 를
> 유지하는 한 풀리지 않았다:
>
> 1. **서비스가 멈춰 있었다.** Firestore 가 결제 미연결로 403 이라 로그인·가입이 전멸.
> 2. **보안 모델이 구조적으로 막혀 있었다.** 결의 user.id 가 앱이 만든 자체 ID 라
>    보안 규칙이 요청자를 식별하지 못했다. 익명 로그인은 웹 API 키만 있으면 누구나
>    할 수 있고 그 키는 번들에 들어 있으니, 인터넷의 아무나가 전 매장 개인정보를 읽었다.
>
> Supabase 로 옮기면 둘 다 사라진다. `auth.uid()` 가 곧 `users.id` 라 DB 가 요청자를 알고,
> 무료 티어라 결제 장벽이 없다. 실시간·인증·DB 가 한 곳에 있어 배포도 단순해진다.

왜 Next.js 인가:

- **공개 매장 페이지 SSR** — `/site/:storeId` 가 서버 렌더되어 검색에 노출된다.
  SPA 구조로는 해결할 수 없는 문제이고, 매장 유치와 직결된다. (Phase 2-1 완료)
- **배포 단일화** — 정적 사이트 + Express 2개 서비스가 하나로 합쳐진다.
- **서버 경계가 언어 차원에서 강제됨** — 토스 시크릿·service_role 키가
  클라이언트 번들로 새는 실수를 구조가 막아 준다.

**완료 기준:** `/site/:storeId` 가 검색에 노출된다. 배포 대상이 하나다.

#### 정해진 것: 다국어는 URL 세그먼트로

`/{ko,en,vi,zh}/site/:storeId`. 서버는 localStorage 를 볼 수 없고, 무엇보다
검색엔진이 언어별 페이지를 각각 색인하려면 URL 이 갈라져 있어야 한다
(베트남·중국 손님 유입까지 노리는 게 SSR 로 옮기는 이유의 절반이다).
기존 `/site/:id` 링크와 매장이 이미 배포한 QR 은 Accept-Language 를 보고 308 로 넘긴다.

#### 남은 위험: 화면이 두 벌

전환 전까지 매장 사이트가 SPA(`src/pages/StoreSite.tsx`)와 Next(`apps/site`) 두 곳에 있다.
오래 방치하면 반드시 어긋난다. 전환하거나, 전환하지 않기로 했다면 `apps/site` 를 지우는 게 낫다.
절차는 `apps/site/README.md`.

### Phase 3 — 보안 규칙 재설계 (규칙·테스트 완료 / 전환 대기)

**지금 상태가 왜 문제인가.** 결의 `user.id` 는 `generateId()` 로 만든 자체 ID 라
Firebase 익명 토큰의 uid 와 아무 관계가 없다. 그래서 규칙에 걸 수 있는 게
`request.auth != null` 뿐인데, 익명 로그인은 **웹 API 키만 있으면 누구나** 할 수 있고
그 키는 클라이언트 번들에 들어 있다. 즉 인터넷의 아무나가 전 매장의 손님 개인정보를
읽고 주문·쿠폰을 조작할 수 있다. 에뮬레이터로 재현해 `firestore.rules.test.ts` 에
5건으로 고정해 두었다.

- [x] **규칙 테스트 기반 구축** — `npm run test:rules` (Firestore 에뮬레이터).
      현재 규칙이 지키는 것 8건 + 못 막는 것 5건.
- [x] **v4 규칙 작성 + 증명** — `firestore.v4.rules`, 검증 33건.
      매장 간 격리(읽기·쓰기·생성·삭제·매장 이전)와 권한 상승 차단을 실제로 막는 것 확인.
- [x] ~~**로그인을 서버로 이전**~~ — Supabase Auth 로 대체됐다(Phase 4).
- [x] ~~v4 배포 + 구 규칙 제거~~ — Firestore 를 떠나면서 규칙 자체가 사라졌다.
      v4 규칙이 증명하려던 것(매장 격리·권한 상승 차단)은 RLS 가 맡고,
      그 검증은 `supabase/tests/rls.sql` 로 옮겼다.
- [ ] 접근성·성능 예산 도입

#### 왜 규칙만 바꿔서는 안 되는가

v4 는 Custom Token 의 claims(`role`·`staffLevel`·`employerStoreId`·`employerStatus`)로
요청자를 식별한다. 그 토큰은 서버가 발급해야 하고, 서버가 발급하려면 **자격 증명을
서버에서 검증**해야 한다. 그런데 지금 로그인은 클라이언트가 `users` 전체를 받아
전화번호·비밀번호를 대조하는 방식이다. 토큰 발급 엔드포인트만 먼저 만들면
"아무 id 나 달라고 하면 그 사람으로 로그인되는" 더 큰 구멍이 된다.

그래서 순서는 이렇다:

1. `POST /api/auth/login` — 서버가 Admin SDK 로 자격 증명을 검증하고
   `createCustomToken(user.id, claims)` 반환
2. 클라이언트는 `signInWithCustomToken` 으로 로그인, `users` 전역 구독 제거
3. 등급 변경 시 `setCustomUserClaims` + 클라이언트 `getIdToken(true)` 강제 갱신
4. `firestore.v4.rules` 배포

1~2 는 장애 중인 로그인 경로를 직접 건드리므로, Firestore 결제가 복구되어
실제 데이터로 검증할 수 있게 된 뒤에 착수하는 것이 안전하다.

#### v4 가 아직 하지 않는 것

- **직원 등급별 컬렉션 게이트.** 어느 컬렉션이 몇 등급부터 필요한지는 화면 사용을
  실측해야 안다. 추측해서 넣으면 직원이 일을 못 한다. 등급은 당분간
  클라이언트 가드(`src/lib/staffAccess.ts`)가 1차 방어선으로 남는다.
- **사장님 간 손님 정보 격리.** 손님 계정에는 `storeId` 가 없어서 매장으로 나눌 수 없다.
  닫으려면 "이 손님이 방문한 매장" 링크가 필요하고 그건 데이터 모델 변경이라 별도 결정이다.
  그래도 v3.1(인터넷의 아무나)에서 v4(로그인한 사장님)로는 큰 폭의 축소다.

## 이번 재작성에서 하지 않는 것

- ~~**Firebase 교체**~~ — 방향이 바뀌었다. Supabase 로 이전한다(위 참고).
  다만 **FCM 푸시는 Firebase 에 남긴다** — Firestore 와 별개 제품이고,
  Supabase 에 대응물이 없으며, 무료다.
- **기능 추가** — 재작성 중에 기능을 얹으면 회귀의 원인을 구분할 수 없게 된다.
- **UI 전면 재디자인** — 구조 이행과 시각 개편을 동시에 하면 둘 다 검증이 안 된다.
  필요하면 Phase 2 완료 후 별도로 다룬다.

### 왜 FCM 만 남기나

FCM 은 Firestore 와 별개 제품이고 무료다. 그리고 웹 푸시 구독은 브라우저가
특정 발신자(VAPID 키)에 묶어 발급하므로, 공급자를 바꾸면 **모든 사장님이 알림을
다시 허용해야 한다.** 얻는 것 없이 그걸 요구할 이유가 없다.

경계는 `src/lib/firebase.ts` 하나로 좁혀 두었다. 앱 핸들만 내보낸다 —
Firestore 핸들·익명 로그인·컬렉션 목록을 남겨 두면 새 코드가 그리로 붙는다.

### 이전으로 사라진 결함

- **로그인에 자격 증명이 없던 문제.** 전화번호가 맞으면 그대로 로그인이었다.
  이제 문자를 받거나 소셜 공급자가 확인해 줘야 세션이 생긴다.
- **매장 간 격리 부재.** RLS 가 `auth.uid()` 기준으로 강제한다.
- **권한 상승.** 등급·역할·소속을 본인이 바꾸는 것을 트리거가 막는다.
  이전에는 update 만 막고 있었는데, **가입(insert) 쪽이 비어 있었다** —
  새 계정을 만들면서 남의 매장 승인 직원으로 들어갈 수 있었다. 같이 막았다.
- **남의 매장 정산 키 덮어쓰기.** 토스 시크릿 저장이 "로그인했는가"만 확인하고
  매장 id 는 요청 본문을 믿었다. 이제 토큰에서 읽는다.

### 이전 중에 드러난 것들

옮기는 과정에서 원래 증상("회원가입·로그인이 안 된다")과 같은 자리의 결함이
새 스택에서도 재현됐고, 그 밖에도 조용히 실패하던 경로가 드러났다.
자세한 내용은 커밋 메시지에 있다.

- `save_doc` 이 `users.role` 을 채우지 않아 **가입이 통째로 실패**했다.
- 문서 id 가 uuid 로 고정돼 있어, 앱이 쓰는 **결정적 id(멱등키)** 다섯 경로가
  전부 실패했다(사장님 가입 시 기본 테이블 15개 생성 포함).
- `orders.customerId` 가 빈 문자열을 uuid 로 캐스팅해 **토스 POS 매출이 한 건도
  들어오지 않았다**(카운터 결제라 손님 계정이 없다).
- `pairing_codes`·`merchant_map` 이 어댑터와 어긋나 페어링·POS 연동이 죽어 있었다.
- 예약이 트랜잭션 없이 옮겨질 뻔했다 — 그대로 뒀으면 **더블북**이 되살아난다.
  판정은 TypeScript 에 두고 마지막 삽입만 원자적으로 처리하도록 나눴다.

### 남은 경계 (닫지 않은 것)

- **`menus` 는 로그인한 누구나 읽는다**(`using (true)`). 손님이 앉은 가게의
  메뉴를 봐야 하는데 "지금 어느 가게에 있는가"를 나타내는 연결이 데이터에 없다.
  닫으려면 그 연결부터 만들어야 한다.
- **사장님 간 손님 정보 격리.** 손님 계정에 `storeId` 가 없어 매장으로 나눌 수 없다.
  Firestore 시절부터 남아 있는 같은 이유다.
- **푸시 발송 대상.** 인증된 사용자가 관계없는 매장에 정상 종류의 알림을 몇 개
  보낼 수는 있다. 완전히 막으려면 "이 손님이 이 매장에 지금 주문/방문이 있는가"를
  종류마다 확인해야 한다. 지금은 세션 필수 + 사용자당 분당 20회로 좁혀 두었다.
- **직원 등급별 컬렉션 게이트.** 어느 컬렉션이 몇 등급부터 필요한지는 화면 사용을
  실측해야 안다. 추측해서 넣으면 직원이 일을 못 한다. 클라이언트 가드
  (`src/lib/staffAccess.ts`)가 1차 방어선으로 남는다.

### 검증

- `supabase/tests/rls.sql` — 매장 격리·권한 상승 차단.
  Firestore 규칙 테스트 46건이 하던 질문을 옮겼다.
- `node scripts/db-doctor.mjs` — 접속·스키마·RLS·문서 API·인증·문자 발송을
  앱이 밟는 순서대로 찔러 어느 단계가 끊겼는지 짚는다.
